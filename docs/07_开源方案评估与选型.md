# 07 开源方案评估与选型

> 本文回答最初的问题：“有哪些开源方案可以直接改？”并说明本项目为什么选当前栈、哪些建议没有直接采用。

## 1. 选型结论

| 需求 | 选型 | 理由 |
|---|---|---|
| 图像/特征/拼接 | OpenCV 4.12（Apache-2.0） | ORB/SIFT、RANSAC、warp、Stitcher 成熟；C++ 底层，Python 易用 |
| 数值 | NumPy | 矩阵/图像运算标准 |
| 桌面 UI | PyQt6（GPLv3/商业） | QGraphicsView 图层、缩放/拾取、QDockWidget 完整；开发快 |
| 打包 | PyInstaller（GPL + 例外） | Windows onedir 稳定；无需目标机 Python |
| 可选 YOLO | Ultralytics YOLO（AGPL-3.0/企业许可） | 生态好、训练快；但许可与包体需评估 |
| 标注工具 | CVAT（MIT）/ Label Studio（Apache-2.0 社区版） | 训练数据标注；不建议把其运行时嵌入桌面端 |
| 参考项目 | OpenPnP（GPLv3） | 相机/轴标定、视觉流水线思路可借鉴，代码许可需注意 |
| 离线全景 | Hugin（GPL2）/ PTGui（商业） | 散图人工拼图；不适合实时闭环 |

> **重要许可提醒**：PyQt6 是 GPLv3/商业双许可；Ultralytics YOLO 是 AGPL-3.0。闭源商业分发前必须采购相应商业许可或替换（PySide6 为 LGPL；YOLO 可用其他 Apache 模型或购买企业许可）。详见 `THIRD_PARTY_NOTICES.md`。

## 2. 可选方案对比

### 2.1 视觉与跟踪

| 方案 | 优点 | 缺点 | 是否采用 |
|---|---|---|---|
| OpenCV ORB + RANSAC | 快、无训练、适合平面小运动 | 重复纹理/模糊敏感 | 主跟踪 |
| OpenCV SIFT | 尺度/旋转更稳 | 慢；专利已过期但计算重 | 散图拼接 |
| 模板匹配 | 极快，适合固定定位孔 | 全图搜索慢；旋转/缩放不鲁棒；需 ROI | 可作为 fiducial 快速锁定补充 |
| 相位相关 | 亚像素平移，快 | 只适合平移/小旋转 | 未用；可做机台模式校验 |
| ECC | 像素级对齐 | 慢、易陷局部最优 | 未用 |
| 单应性 Homography | 可处理透视/倾斜 | 8 自由度更易过拟合重复纹理 | 仅备用/未来标定 |
| ORB-SLAM/COLMAP | 完整 6DoF/SLAM | 对本场景过度复杂；平面 PCB 不需要 | 不采用 |

### 2.2 UI / 渲染

| 方案 | 评价 |
|---|---|
| PyQt6 QGraphicsView | 本项目采用：图层、选中、变换、缩放、Dock、表格齐全 |
| PySide6 | API 近似，LGPL，商业友好；**建议商业版迁移** |
| Electron + Canvas/Konva | Web 技术栈、跨平台；与 Python/OpenCV 进程通信复杂；4K 视频性能需额外优化 |
| Dear PyGui | 性能好，但控件/中文/表格生态弱于 Qt |
| OpenGL 自绘 | 可做高帧率，但交互/文字/无障碍开发量大 |

### 2.3 目标检测

| 方案 | 许可 | 评价 |
|---|---|---|
| 传统形态学（本版） | 自研 | 无需数据，输出候选，不分类 |
| YOLOv8/11 Ultralytics | AGPL-3.0 或企业许可 | 训练/部署简单；商业需许可；包体大（PyTorch） |
| MMDetection / Detectron2 | Apache-2.0 | 灵活，部署链更复杂 |
| Faster R-CNN | 各实现不同 | 精度好但慢，不适合实时 |
| SAM 系列 | Apache-2.0（部分权重许可不同） | 分割强，不适合分类；可辅助标注 |
| 模板匹配 + 分类器 | 自研 | 仅适合固定板型/固定光照 |

### 2.4 标注/数据

- **CVAT**：视频/图像标注、团队协作；可导出 YOLO/COCO。
- **Label Studio**：通用标注，社区版 Apache-2.0；企业功能收费。
- **Labelme**：轻量，MIT；适合框/多边形，但团队管理弱。
- 结论：用 CVAT/Label Studio 做数据集，桌面端不嵌入完整标注平台；本项目的“人工核对”是生产流程的一部分，不是训练标注。

### 2.5 拼图

- **OpenCV Stitcher（PANORAMA/SCANS）**：一行调用，但对 PCB 重复焊盘/低纹理容易失败；本项目没有直接依赖。
- **Hugin/PTGui**：离线高质量全景，适合散图；不能实时集成。
- **自研有序配准 + 内容校验**：本项目采用，因为拍摄顺序/重叠已知，可控性更高。
- **视频扫描 + 位姿累加**：主路径；仍需回环闭合。

### 2.6 参考项目

- **OpenPnP**（GPLv3）：开源贴片机，包含相机/轴标定、视觉定位、吸嘴偏移等；其“相机坐标↔机台坐标”思路值得参考，但直接复用代码受 GPL 约束。
- **OpenCV 官方 stitching/sfm 示例**：算法参考。
- **Labelme/Label Studio**：UI 交互参考（框选、标签、列表），不建议直接嵌入其重型依赖。
- **Hugin**：离线拼图质量参考。
- 没有找到“正上方相机 + 手动显微镜 + 参数气泡 + 人工核对”完全现成且可直接商用的开源项目；定制不可避免。

## 3. 对初始技术建议的复核

最初对话中的总体方向（OpenCV + PyQt + ORB/仿射 + 局部/全局）是正确的，但若干代码片段不能直接用于生产：

### 3.1 模板匹配定位孔代码

```python
base_points = np.float32(list(base_reference_points.values()))
...
current_points = []
for name, template in self.templates.items():
    ...
    if max_val > 0.6:
        current_points.append(...)
    else:
        return self.last_matrix
...
src_pts = self.base_points[:len(current_points)]
```

问题：

1. **点位错位**：某个模板缺失时，`current_points` 少一个，但 `base_points[:len]` 仍从第一个开始取，导致配对错乱。必须用 `name -> base_point` 的显式映射，而不是切片。
2. **全图模板匹配开销大**：4K 全图 + 多个模板每帧搜索会非常慢；应在上一位置附近 ROI 搜索，或改用 ORB/相位相关。
3. **阈值 0.6 过低**：PCB 重复焊盘多，容易误匹配；应结合多模板几何一致性/RANSAC。
4. **常量写法**：`cv2.matchTemplate.TM_CCOEFF_NORMED` 不是正确 API，应为 `cv2.TM_CCOEFF_NORMED`。
5. **少于 3 点**：2 点估计相似变换不稳定；至少 3 点，且做内点校验。

### 3.2 视频拼图示例

```python
self.accumulated_H = np.dot(self.accumulated_H, np.linalg.inv(M))
self.global_canvas = np.where(mask > 0, warped, self.global_canvas)
```

问题：

1. **矩阵方向**：`M` 是 current→last 还是 last→current，必须明确；复合顺序错误会导致整张图飞掉。本项目固定 `Pose_world(cur) = Pose_world(last) @ T(cur→last)`。
2. **固定 5000×5000 画布**：首帧贴中心，扫描超出边界会被裁掉；应动态计算联合包围盒。
3. **全画布 `np.where`**：每帧对 2500 万像素重新分配/复制，内存和耗时高；应只处理 warp 后的 ROI。
4. **硬覆盖无羽化**：接缝明显、曝光差会形成亮暗带；应做羽化/多频段融合。
5. **只用上一帧且取距离最近的 20 个匹配**：没有 ratio test，重复纹理易错；应 KNN + ratio + RANSAC + 内容相关性校验。
6. **漂移**：纯帧间累加会漂移；长扫描需要回环闭合/位姿图优化。

### 3.3 “视频扫描一定比散图简单”

方向正确，但不是无条件：

- 视频帧间重叠高，**配准**更简单；
- 但误差**累加**、快速运动模糊、曝光变化、回环误差是新的工程问题；
- 散图如果由机台按已知网格拍摄，反而可用机台坐标做初值，精度更高；
- 最优方案是“机台坐标提供初值 + 视觉精配准 + 回环优化”。

本项目把视频扫描作为主路径，同时保留散图拼接，是折中而非绝对结论。

## 4. 第三方库许可摘要

| 组件 | 许可 | 备注 |
|---|---|---|
| OpenCV | Apache-2.0 | 可商用；部分 contrib 模块有额外专利/许可，需核对 |
| NumPy | BSD-3-Clause | 可商用 |
| PyQt6 / Qt6 | GPLv3 / 商业 | **闭源分发需商业许可或改 PySide6** |
| PySide6 / Qt6 | LGPLv3 / 商业 | 动态链接可满足 LGPL，需遵守条款 |
| PyInstaller | GPL-2.0 + 特殊例外 | 打包非 GPL 程序通常可用，需保留许可 |
| Ultralytics YOLO | AGPL-3.0 / 企业 | 商业闭源需企业许可 |
| CVAT | MIT（社区版） | 以官方仓库为准 |
| Label Studio | Apache-2.0（社区版） | 企业功能另授权 |
| OpenPnP | GPLv3 | 参考设计，直接复用需开源 |
| Hugin | GPL2 | 离线工具，不嵌入 |

> 本表不构成法律意见。发布前请让法务核对实际版本和链接方式。

## 5. 最终建议

1. **保留 OpenCV + Qt 桌面路线**：实时性、交互、部署都合适。
2. **优先把真实数据接进来**：合成板只能验证算法，现场反光/模糊/重复纹理才是难点。
3. **扫描加回环闭合**：这是视频扫描从“能用”到“稳定”的关键。
4. **YOLO 只在有数据后上**：先用传统候选 + 人工核对跑通流程。
5. **商业分发前解决 PyQt6/YOLO 许可**：PySide6 + Apache 模型是最稳的组合。
